# dxfsign — техническое решение

**ТЗ:** утилита просмотра и правки DXF на сетевом диске. Каждое изменение сохраняется и
автоматически подписывается письмом `.eml` на выбранный адрес, рядом кладётся `.txt` с перечнем
изменений; навигация по папкам — по вручную ведёмому каталогу в файле конфигурации.
Дополнения владельца по ходу: **правится в первую очередь текст надписи**, после правки
**спрашивается номер провода**, можно оставить **комментарий в свободном формате** (он идёт в
перечень предлагаемых изменений), **новый DXF перезаписывается, а старый уезжает в подпапку версий**.

Дата решения: 2026-11-19. Всё, что ниже помечено «проверено», проверено на этой машине реальным
запуском, а не рассуждением.

---

## 1. Разбор требований

Проверяемость: **П** — проверяется автоматически (тест/замер), **Р** — проверяется ревью/показом,
**Н** — не проверяется без человека или внешней системы.

| # | Требование (из ТЗ и уточнений) | Проверяемо | Как проверено в скелете |
|---|---|---|---|
| 1 | Просмотр DXF: LINE, CIRCLE, LWPOLYLINE | П | разбор + round-trip тесты, 5 видов сущностей |
| 2 | **Правка текста надписи** (главное) | П | автомат `EditSession`, диалог, паритет «было→стало» |
| 3 | **После правки — ввод номера провода** | П | правка не применяется без валидного номера (тест) |
| 4 | **Свободный комментарий → в перечень изменений** | П | запись `COMMENT` в журнале, печать в `.txt`, заголовок `X-DXFSIGN-Comments` |
| 5 | Сохранение: рабочий файл перезаписывается | П | E2E: хеш файла на диске == `X-DXFSIGN-New-SHA256` |
| 6 | **Старый DXF — в подпапку версий** | П | E2E: `_VERSIONS/<имя>__<ts>_<seq>.dxf`, содержимое = прежние байты |
| 7 | Автописьмо `.eml` на заданный адрес | П (спул), **Н** (SMTP) | MIME-письмо разобрано независимо парсером Python `email` |
| 8 | `.txt` с перечнем изменений рядом с чертежом | П | файл + содержимое в E2E |
| 9 | Подпись сохранения | П | HMAC-SHA256, векторы RFC 4231 |
| 10 | Навигация по каталогу из конфига | П | INI-парсер, `resolve()` с Unicode-регистром, команда `catalog` |
| 11 | Ровно один язык из Pascal/Ada/Rust/Zig | Р | Rust, обоснование в §2 |
| 12 | DOP + POP, конфликт разделить | Р | §3: DOP — геометрия/кадр, POP — ФС/почта/подпись/версии |
| 13 | Brutalism + Swiss с реализацией | П/Р | §5: числа + снимок кадра из кода |
| 14 | Windows 7 и ранее — жёстко | **П (част. конфликт)** | §2.4: PE-импорты UCRT; вердикт «нужен KB2999226» |
| 15 | Строго типизированная память | Р | Rust: ни одного `unsafe` в модели, `unsafe` только в FFI-слое Win32 |
| 16 | Нет GC в главном цикле | П | 200 кадров → **0 аллокаций** (потоковый счётчик) |
| 17 | SIMD там, где оправдано | П | AVX2-ядро проекции, **×15.2** к скаляру на 42 500 точках |
| 18 | Сложность горячих операций названа | Р | §4 и §6, с поведением на 10× данных |

**Чего в ТЗ нет** (и это не додумано, а вынесено в решения владельцу): формат номера провода,
правило хранения версий (сколько), транспорт письма (SMTP или файл-спул), формат файла каталога,
кодировка DXF (принята CP1251 по `$DWGCODEPAGE`), поведение при потере сети, состав поддерживаемых
сущностей DXF.

### 1.1 Таблица противоречий

| Конфликт | Вариант A | Чем платим | Вариант B | Чем платим | Рекомендация |
|---|---|---|---|---|---|
| **«DXF-редактор» vs объём** | Полный редактор (snap/osnap, блоки, размеры, штриховки) | 6–12 мес. работы, и всё равно проигрыш AutoCAD | Узкий редактор надписей + 4 вида геометрии | Годится не для всех файлов: `INSERT`/`DIMENSION` теряются | **B** — но с жёстким предохранителем: файл с неподдержанными сущностями **не перезаписывается** (см. §3.5) |
| **DOP vs POP** | DOP везде | Протоколы/динамика в SoA-массивах невыразимы, каждое устройство тянет свою структуру | POP везде | Виртуальные вызовы в кадре, кэш-промахи на геометрии | **Разделить**: DOP для точек/примитивов/кадра, POP для ФС/почты/подписи/хранилища версий — 1 вызов на сохранение, не в кадре |
| **«Автоподпись через почту» vs безопасность** | Автоотправка на SMTP с паролем в конфиге | Пароль на сетевом диске = компромисс; молчаливая потеря писем при сбое SMTP | Спул `.eml` + отдельный агент доставки | Нужен агент (планировщик/сервис), задержка доставки | **B**: утилита пишет `.eml` атомарно, доставку делает сервис с нормальной аутентификацией. Подпись — HMAC, ключ из окружения/файла, не из конфига |
| **Win7 vs современные тулчейны** | Rust 1.78+ (Tier 1) | Официально **Win10 минимум** (ProcessPRNG, CMPXCHG16B/SSE3 baseline) — на Win7 не стартует | Rust 1.77.2 (пин) или Tier 3 `*-win7-*` | Пин: нет обновлений безопасности; Tier 3: nightly + `-Z build-std` + Windows SDK через `xwin` | **Пин 1.77.2** для Win7-сборки (проверено: собирается), основная сборка — stable. CMPXCHG16B/SSE3 у всех x86_64, которые реально стоят с Win7 SP1 |
| **Win7 vs UCRT** | Mingw-w64/UCRT (как собрано) | Нужен KB2999226 на чистой Win7 SP1 | MSVC + Win7 SDK + msvcrt-mingw | Не установлено на этой машине; msvcrt-mingw надо ставить отдельно | Оставить UCRT (KB2999226 — стандартное обновление, его требует и VC++2015+); либо собрать msvcrt-вариант, если в цеху запрещены обновления |
| **Win7 vs SIMD** | `target-cpu=native`/AVX2 всегда | На Westmere/Sandy Bridge (типичная Win7-машина) — **SIGILL** | Baseline + рантайм-детект | Чуть больше кода, +1 ветка на кадр | **B**: SSE2-baseline, AVX2 только после `is_x86_feature_detected!`, скалярный хвост с тем же клампингом |
| **Номер провода обязателен vs скорость правки** | Применять правку сразу, номер спрашивать потом | На диске оказывается правка без трассировки | Правка **не применяется**, пока номер не принят | Один лишний шаг в диалоге | **B** — на сетевом диске «правка без номера» недопустима; для серии есть prefill последнего номера |
| **Письмо на каждый чих** | Письмо на каждую правку | Поток писем, почта превращается в лог | Одно письмо на сохранение (пачка правок) | Нужен явный Ctrl+S | **B**: письмо = сохранение; правки копятся в журнале |

## 2. Стек: Rust, и что он НЕ даёт

### 2.1 Почему Rust, а не Pascal/Ada/Zig

| Критерий (из ТЗ) | Rust | Free Pascal | Ada (GNAT) | Zig |
|---|---|---|---|---|
| Нет GC | ✔ (нет рантайма сборки мусора) | ✔ | ✔ (есть `pragma Restrictions(No_Finalization)`) | ✔ |
| Строгая типизация памяти | ✔ владение + заимствование на этапе компиляции | ✖ (указатели как в C) | ✔ (SPARK — сильнее всех) | ✔ (частично, comptime + проверки) |
| SIMD | ✔ `std::arch` интринсики, AVX2/AVX-512 | ✖ интринсиков нет: только inline asm или внешний C (подтверждено списком fpc-pascal) | ◐ `GNAT.SSE*` — только часть наборов, AVX2 зависит от версии GNAT | ✔ `@Vector`, отличный кодоген |
| Win7 | ◐ 1.77.2 пин или Tier 3 `win7` таргеты | ✔ Win32/Win64 нативно | ◐ зависит от сборки GNAT CE | ✖ **с 0.11 минимум Windows 10** (официально) |
| Экосистема/переиспользование | ✔ есть наш `cadcraft` (DXF-тег-ридер) | ✖ | ✖ | ✖ (pre-1.0, ломается между версиями) |
| Безопасность FFI | ✔ `unsafe` локализуется | ✖ | ◐ | ✔ |
| Сборка на этой машине | ✔ rustc 1.97.1 + 1.77.2 (проверено) | ✖ не установлен | ✖ не установлен | ✖ не установлен |

Итог: **Rust** — единственный из четырёх, который одновременно даёт отсутствие GC, интринсики
SIMD, безопасность памяти и уже существующие наработки по DXF. Zig отвергнут жёстким конфликтом
с Win7 (это не «сложность», а прямое противоречие требованию), Ada/Pascal — отсутствием
интринсиков (Pascal) и экосистемы (оба).

### 2.2 Что Rust здесь НЕ даёт (честно)

1. **Win7 — это уже не «бесплатно».** Начиная с 1.78 официальный минимум для `*-pc-windows-*` —
   Windows 10. Живые пути: пин `1.77.2` (проверено, собирается) либо Tier 3
   `x86_64-win7-windows-msvc` с `-Z build-std` и SDK через `xwin`. Второй путь — nightly в CI.
2. **UCRT.** Сборка Mingw-w64 (в т.ч. от rustup) линкует `api-ms-win-crt-*`. На Win7 SP1 это
   работает только с KB2999226 (или при раскладке UCRT рядом с exe). Проверено `objdump -p`:
   импортов `vcruntime140.dll`/`msvcr120.dll` нет, только `KERNEL32`, `GDI32`, UCRT, `ntdll`.
3. **POP в Rust дороже, чем в Swift.** `dyn Trait` — виртуальный вызов ~2–5 нс и запрет инлайна;
   «протокол с ассоциированными типами» выражается дженериками, а значит мономорфизацией и ростом
   кода. Поэтому POP применён только на границах (ФС/почта/подпись/версии), где вызов идёт раз в
   сохранение, а не в кадре.
4. **Нет рефлексии для DXF.** Обход тегов пишется руками по справочнику Autodesk — никакой
   сериализации «из коробки».
5. **Нет встроенного MIME/SMTP.** Письмо собирается своим кодом (RFC 5322/2047/4648) — 24 КБ
   кода, зато ноль зависимостей и предсказуемая сборка под Win7.
6. **Не даёт `catch_unwind` при `panic = "abort"`.** Паника = падение процесса; в кадре паник
   быть не может по построению (все индексы проверяются, `Overflow` возвращается как ошибка).

### 2.3 Что выбрано внутри Rust

* **Ноль внешних крейтов** — сборка под Win7 не должна тянуть граф зависимостей, который сам
  потребует Win10 API.
* `panic = "abort"`, `lto = "fat"`, `codegen-units = 1` — 624 КБ один файл, без DLL.
* `target-cpu` — baseline; AVX2 выбирается в рантайме.

### 2.4 Вердикт по Win7 (проверено)

```
objdump -p dxfsign.exe | grep "DLL Name"
  GDI32.dll, KERNEL32.dll, ntdll.dll,
  api-ms-win-crt-{heap,stdio,string,math,locale,environment,runtime,private}-l1-1-0.dll
```

* **Один файл**, без .NET, без VC++ redist, без Python. 624 640 байт.
* **Windows 10/11** — работает как есть.
* **Windows 7 SP1** — работает при установленном **KB2999226** (Universal C Runtime). Без него
  exe не стартует — это ограничение тулчейна, а не кода; названо как конфликт в §1.1.
* Собрать «совсем без UCRT» можно msvcrt-сборкой Mingw-w64 либо MSVC + Windows 7 SDK; на этой
  машине таких тулчейнов нет, поэтому заявлять «проверено» не буду.

## 3. Архитектура

### 3.1 Модули и границы

```
main.rs      CLI + потоковый счётчик аллокаций + оконный режим-маршрутизация
 ├ config.rs   INI: адрес, спул, каталог сетевого диска, ключ (не печатается)
 ├ dxf.rs      ASCII DXF: теги, LINE/CIRCLE/LWPOLYLINE/TEXT/MTEXT + запись и CP1251
 ├ doc.rs      DOP-модель: SoA-массивы, индексы, журнал правок, хеш состояния
 ├ text.rs     арена строк (StrRef) + CP1251↔UTF-8 + поле ввода фиксированной ёмкости
 ├ edit.rs     автомат правки: ТЕКСТ → НОМЕР ПРОВОДА (обязателен) → КОММЕНТАРИЙ
 ├ journal.rs  журнал правок между `edit` и `save` (TSV-сайдкар, percent-escaped)
 ├ save.rs     протокол сохранения: ротация → перезапись → .txt → .eml → якорь цепочки
 ├ eml.rs      RFC 5322 + MIME multipart + RFC 2047 + RFC 4648
 ├ sha256.rs   SHA-256, HMAC-SHA256, base64 (векторы FIPS/RFC в тестах)
 ├ ports.rs    POP-контракты: FileSource / Signer / MailTransport / VersionStore
 ├ render.rs   камера, AVX2-проекция, растеризатор, раскладка Brutalism+Swiss
 ├ win32.rs    GDI-типографика (системная Arial, 1-битная маска) — без крейтов
 └ window.rs   окно Win32: кадр, выбор надписи, F2/F3, Tab/Enter/Esc, Ctrl+S
```

Правила границ:
1. `doc`/`dxf`/`render` **не знают** про диск, почту и подпись — только память.
2. Всё внешнее — только через трейты `ports`, по одному вызову на сохранение.
3. `window` не знает, куда писать `.eml`: получает хук `fn(&Doc) -> String` от `main`.
4. `render` не знает, чем рисуется текст: `trait TextPainter` (GDI в окне, приближённый в тестах).

### 3.2 DOP: структуры данных

```rust
// точки — раздельно, ровно под AVX2-загрузку 4×f64 без gather
xs: Vec<f64>, ys: Vec<f64>,
segs:     Vec<Seg    { a: u32, b: u32, layer: u16 }>,        // индексы, не указатели
circles:  Vec<Circle { c: u32, r: f64, layer: u16 }>,
polys:    Vec<Poly   { first: u32, len: u32, closed: bool, layer: u16 }>,
poly_verts: Vec<u32>,                                        // одна аллокация на все полилинии
texts:    Vec<TextEnt{ pos: u32, height: f64, rot_deg: f64, kind: u8, s: StrRef, wire: StrRef }>,
arena:    TextArena,                                         // байты всех строк одним буфером
```

* **Индексы вместо указателей**: `Handle { slot: u32, gen: u32 }` — 8 байт, Copy; поколение ловит
  висячую ссылку после удаления (нет UB, как с висячим указателем).
* **Пулы**: свободные слоты — стек индексов; удаление не отдаёт память ОС, поэтому кадр не растёт.
* **Строки в арене**: правка не перезаписывает старое значение, а дописывает новое — поэтому diff
  «было→стало» и хеш версии всегда имеют оба состояния. Мусор считается, `compact()` — только вне кадра.
* **Слой как `u16`-индекс** в таблицу слоёв, имя слоя — `StrRef` в той же арене.

### 3.3 POP: контракты

```rust
trait FileSource {                    // локальный/сетевой путь, память для тестов
    fn read(&self, path:&str) -> io::Result<Vec<u8>>;
    fn write_atomic(&mut self, path:&str, data:&[u8]) -> io::Result<()>;   // tmp + rename
    fn create_dir_all(&mut self, p:&str) -> io::Result<()>;
    fn move_file(&mut self, from:&str, to:&str) -> io::Result<()>;
    fn list(&self, dir:&str) -> io::Result<Vec<DirEntryRec>>;
    fn remove_file(&mut self, p:&str) -> io::Result<()>;
}
trait Signer      { fn sign(&self, canonical:&[u8]) -> Option<[u8;32]>; fn key_id(&self)->&str; }
trait MailTransport { fn deliver(&mut self, raw:&[u8], name:&str) -> io::Result<String>; }
trait VersionStore  { fn append(&mut self, rec:&VersionRecord) -> io::Result<()>;
                      fn head(&self)->Option<[u8;32]>; fn count(&self)->u64; }
trait TextPainter   { fn text(...); fn measure(...) -> i32; }     // рендер ↔ шрифтовой бэкенд
```

`Signer::sign -> Option` — принципиально: нет ключа → `X-DXFSIGN-Unsigned`, а не «подписано пустым
HMAC». `MailTransport` в скелете один: спул-каталог (`.eml` = запись, которую забирает агент).

### 3.4 Горячий путь

| Операция | Сложность | Замер (эта машина) | На 10× данных |
|---|---|---|---|
| Открытие/разбор 42 500 сущностей, 1.32 МБ | O(B) по байтам | ~65 мс end-to-end (`inspect`, включая старт процесса) | ~650 мс на 425 тыс. сущностей — приемлемо; предел — 4 ГБ адресуемого `Vec` (ограничение `u32`-индексов = 4.29 млрд элементов) |
| Проекция точек (кадр) | O(N) | скаляр 7.9 нс/точка, **AVX2 0.5 нс/точка (×15.2)** | 425 тыс. точек: 0.2 мс вместо 3.4 мс — по-прежнему кадр |
| Растеризация отрезков | O(Σ длин в пикселях) | — | растёт с масштабом, не с числом сущностей; ограничение — площадь окна |
| Окружность | O(r) (8 точек/шаг) | — | радиус — пиксели, ограничен окном |
| Правка текста | O(1) + копия строки | — | не зависит от размера чертежа |
| Хеш состояния (версия) | O(N) | SHA-256 по SoA | 425 тыс. точек ≈ 6.8 МБ данных — 20–30 мс |
| Сохранение (протокол) | O(N + B) | 4 записи файла + письмо | линейно по размеру файла; узкое место — SMB, а не CPU |
| `collect_wires` | O(K²) при K ≤ 1024 | ≤ 1 мс | **при 10 000 правок станет 10⁸** — надо заменить на сортировку/хеш (см. §6) |
| Hit-test надписи в окне | O(T) | — | 10 000 надписей — 0.1 мс |

### 3.5 Предохранитель по неподдержанным сущностям

`ParseStats.skipped` считает всё, что не LINE/CIRCLE/LWPOLYLINE/TEXT/MTEXT. Если `skipped > 0`,
перезапись файла запрещена (иначе `INSERT`/`DIMENSION` будут потеряны молча). Сейчас это
диагностика в `inspect`; включение жёсткого запрета в `save` — решение владельца (§8).

## 4. Компилируемый скелет: что реально собрано

`cargo build --release` → `dxfsign.exe`, 624 640 байт, ноль зависимостей.
`cargo test` → **49 тестов, все зелёные** (и последовательно, и параллельно).

| Что | Как проверено | Результат |
|---|---|---|
| SIMD-ядро проекции | AVX2 vs скаляр на 1003 точках, допуск 1 px; отдельно — inf/1e300 | совпадает; клампинг держит i32 |
| Кадр без аллокаций | потоковый счётчик malloc/realloc | **200 кадров → 0 аллокаций** |
| Правка без номера провода | тест автомата | документ не меняется, `Rejected` |
| Комментарий | тест | попадает в журнал, `.txt`, заголовок письма |
| CP1251 ↔ UTF-8 | вектор «Привет» в двух направлениях | без потерь |
| DXF round-trip | 5 видов сущностей | счётчики и геометрия сохраняются |
| XData номера провода | запись/чтение `1001 DXFSIGN` | номер остаётся в самом DXF |
| `.eml` | независимый парсер Python `email` | 3 вложения, RFC 2047-тема декодируется, хеши сходятся |
| Ротация версий | E2E на живом exe | `_VERSIONS/<имя>__20261119-113500_001.dxf` = прежние байты |
| Цепочка версий | `index.tsv` после E2E | строка с prev/new/chain-хешем и номерами проводов |
| Окно Win32 | `open --selftest 1500` | exit 0, окно создаётся и закрывается |

**Дефекты, найденные проверкой (не рассуждением) и исправленные:**
1. Разборщик вызывал вложенные `read_header`/`read_tables`, они съедали `0 SECTION / 2 ENTITIES` —
   геометрия молча не читалась. Переписан в один проход.
2. Журнал правок не переживал переход `edit` → `save`: `.txt` уходил с «правок: 0». Добавлен
   сайдкар `journal.tsv`.
3. Заголовки письма не кодировались по RFC 2047 — тема с кириллицей превращалась в мусор.
4. Индекс цепочки писался в относительный путь (терялась часть каталога) — путь через `parent_dir`.
5. AVX2-хвост (точки, не кратные 4) не клампился → `i32::MIN` на бесконечных координатах.
6. «Затемнение сеткой» под модальным окном давало муар и убивало читаемость чертежа.

**Что НЕ проверено и заявляется как непроверенное:**
* реальная отправка по SMTP (не реализована намеренно, см. §1.1);
* работа на настоящем SMB-шаре (пути `\\srv\...`) — только локальные каталоги;
* запуск на Windows 7 (машины нет; вердикт по PE-импортам, см. §2.4);
* IME-ввод и буфер обмена в окне;
* чертежи с `INSERT`/`DIMENSION`/`XREF` — сознательно вне объёма.

### 4.1 Протокол сохранения (порядок обязателен)

```
1. байты нового DXF в память + SHA-256
2. текущий файл на диске → _VERSIONS/<имя>__<YYYYMMDD-HHMMSS>_<seq>.dxf  (копия,
   затем ПРОВЕРКА: sha256(копии) == sha256(прежнего) — иначе останов)
3. рабочий файл перезаписывается атомарно (tmp + rename)
4. <имя>__<ts>.changes.txt рядом с чертежом
5. _SPOOL/<имя>__<ts>.eml: новый .dxf, прежний .dxf, .txt + X-DXFSIGN-* + HMAC
6. строка якоря в _VERSIONS/index.tsv (prev/new/chain SHA-256, провода)
7. journal.tsv удаляется — проведённая правка не применяется дважды
```

Гарантия при сбое: до шага 3 рабочий файл не тронут; падение на шаге 3 оставляет версию в
`_VERSIONS` (повтор возможен); падение на шаге 4 видно как расхождение `head` индекса с последним
письмом в спуле.

## 6. План работ

| Этап | Объём | Проверяемо | Сложность горячих операций |
|---|---|---|---|
| **E0. Основа (готово)** | модель SoA, DXF 5 видов, текст+правка, номер провода, комментарий, протокол версий, `.eml`, `.txt`, окно, UI-каркас | 49 тестов, E2E, 0 аллокаций в кадре | O(N) кадр, O(B) разбор |
| **E1. Полигон сущностей** (2–3 нед.) | `INSERT`/блоки, `DIMENSION` как геометрия, `HATCH` как контур, `SPLINE`→полилиния для показа | golden-файлы: 20 реальных чертежей цеха, диff по числу сущностей | O(N) без изменений |
| **E2. Доставка почты** (1 нед.) | SMTP-транспорт (SMTPS + STARTTLS), DKIM-подпись не делаем; агент-делитель спула | письмо доходит до тестового ящика, проверка вложений и HMAC на приёмнике | вне кадра |
| **E3. Сетевой диск по-настоящему** (1 нед.) | обработка ERR_NETWORK_BUSY, повтор с backoff, «занято другим» — блокировка `.lock`, журнал операций | тест с отключением шары в середине сохранения, восстановление | O(1) на операции |
| **E4. Проверка целостности** (1 нед.) | команда `verify`: пересчёт цепочки, сверка писем в спуле, детект перезаписи версии в `_VERSIONS` | подмена файла версии → `verify` падает | O(K) по записям цепочки |
| **E5. Производительность 10×** (1 нед.) | заменить `collect_wires` O(K²) на сортировку (O(K log K)); пакетная растеризация; кэш тайлов | бенч на 425 тыс. сущностей: кадр ≤ 16 мс, сохранение ≤ 1 с | см. ниже |
| **E6. Полировка Win7** (3 дня) | решить UCRT vs msvcrt-mingw, CI-матрица `1.77.2` + stable, проверка на реальной Win7-машине | прогон на Win7 SP1 без KB и с KB | — |

**Что будет на 10× данных (425 тыс. сущностей, 13 МБ):**

| Операция | Сейчас | На 10× | Узкое место и что делать |
|---|---|---|---|
| Разбор | 65 мс | ~650 мс | один проход, `Vec` с резервом; при 4 ГБ — перейти на `u64`-индексы или mmap-таблицы |
| Кадр (проекция) | 0.5 нс/точка AVX2 | 0.2 мс на 425 тыс. точек | память; при >8 млн точек — тайловый кэш проекции |
| Растеризация | по площади окна | не меняется | не зависит от числа сущностей, только от зума |
| Правка | O(1) | O(1) | — |
| Хеш версии | O(N) | 20–30 мс | SHA-256 уже быстрый; альтернатива — инкрементальный хеш по изменённым диапазонам |
| `collect_wires` | O(K²), K≤1024 | **10⁸ при 10 000 правок** | заменить на сортировку (E5) — обязательный пункт |
| Сохранение | 4 записи + письмо | линейно по размеру | SMB; письмо на 13 МБ base64 → 17 МБ: нужен лимит и/или ссылка вместо вложения (решение владельца) |

## 8. Что осталось решать владельцу

1. **Формат номера провода.** Принято: 1–24 символа, первый — буква/цифра, далее буквы, цифры
   `. _ / - пробел`. Если есть шифр по ГОСТ/по вашему стандарту — дайте маску, она меняется в одном
   месте (`edit::validate_wire`).
2. **Обязательность номера.** Сейчас без номера правка **не применяется**. Нужен ли режим
   «применить, номер пометить как отсутствующий»?
3. **Хранение версий.** Сейчас `keep_versions = 0` (хранить всё). Сколько версий держать и что
   делать со старыми (удалять/архивировать)?
4. **Транспорт письма.** Спул-каталог + агент (рекомендую) или SMTP прямо из утилиты? Если SMTP —
   какой сервер/аутентификация (пароль в конфиге на сетевом диске — плохая идея).
5. **Адрес получателя** и правило: одно письмо на сохранение (сейчас) или на каждую правку?
6. **Состав сущностей DXF.** Блоки `INSERT`/`DIMENSION` — нужны? Если да, E1 обязателен до внедрения,
   иначе файлы цеха будут отвергаться предохранителем.
7. **Поведение при неподдержанных сущностях.** Разрешить перезапись с предупреждением или
   запретить жёстко (сейчас — только диагностика)?
8. **Windows 7.** Ставить KB2999226 на машины (просто) или собирать msvcrt-вариант (сложнее,
   зато без обновлений)?
9. **Кодировка.** Принята CP1251 по `$DWGCODEPAGE`. Если в цеху есть UTF-8-DXF (2007+ с `\U+`
   эскейпами) — нужен второй путь записи.
10. **Каталог сетевого диска.** Формат INI принят. Нужны ли права/роли (кто какие папки видит)?
